Drivers as data: a hosted platform for portable, AI-authored device drivers

One place where hardware drivers live, get tested against every operating system, and connect to any OS. Hardware makers upload once; OS writers port one runtime and get the whole catalogue; every OS fetches signed drivers through one open protocol. Built end to end by AI, with people doing only what legally or physically needs a person.

01The thesis, sharpened

Linux 7.3-rc1 is close to 41 million lines, and the AMD GPU driver alone is about 16% of it. Most of the kernel is drivers. Any new OS faces the same wall: thousands of devices, each needing code written for that OS. Vendors face the mirror problem: one driver per OS, re-done every time an OS changes its internals.

The claim to build the company on:

Claim

For the long tail of devices, the device-specific part of a driver can be data (a description) plus a small amount of sandboxed logic. The OS only needs a few generic, stable "doors" to the bus and a handful of standard device classes. Then a new OS gets thousands of devices by implementing one runtime, and a vendor writes a device once.

What this plan deliberately does not claim, at least until Phase 4:

  • Not GPUs, not high-speed NIC or NVMe data paths, not boot devices. These need kernel-level performance and early-boot presence. Promising them early would sink credibility.
  • Not "kernels delete their driver code". The near-term pitch is "kernels stop growing for the long tail", and new OSes skip writing it. Removing existing drivers is a decade-scale outcome, not a pitch.
  • Not a stable in-kernel driver ABI. Linux maintainers have refused that for 20 years. Everything we do lives above the kernel boundary, using interfaces the kernel already promises to keep stable.

Beachhead: USB, serial, HID, I²C/SPI sensors and actuators, lab instruments, robotics and maker hardware. These are the devices whose vendors today ship a Windows-only app or nothing, and whose users are on Linux and macOS.

03What history teaches

This idea has been tried in parts several times. Each attempt proves something and leaves a lesson.

PrecedentWhat it provedLesson for us
UDI, Uniform Driver Interface (1998–2004)A portable driver API could work technically across OSes.It died on adoption. Microsoft and Apple never joined, the Linux community saw it as a channel for closed binary drivers, and it ended as SCO's private interface. Never require an OS to adopt us before we deliver value. Run as an ordinary program first.
Devil IDL (OSDI 2000)A declarative register/device description lets a compiler generate access code and check consistency. Writing a Devil spec was up to 5.9× less error-prone than writing C.The "description" half of your plan has research support. Steal its idea of compile-time consistency checks for the validator.
Termite 1 & 2 (NICTA/UNSW, SOSP 2009, OSDI 2014)Drivers can be synthesized from a device spec plus an OS-interface spec, with performance on par with hand-written drivers.Termite-1 output was correct but unmaintainable. Termite-2 added user-guided synthesis and spec debugging. Keep a human in the loop and make the description the thing people maintain, not generated code.
HID-BPF and udev-hid-bpf (Linux, 2024–2026)Linux already accepts small, sandboxed, per-device programs that fix hardware without a new kernel driver. Red Hat maintainers routinely ship tablet and keyboard fixes this way.The closest living proof of your model inside Linux. Cite it in every kernel conversation, and support HID-BPF as an output target.
LVFS + fwupdVendors will upload to a neutral, signed, Linux-friendly hosting service: 179 vendors and 135M+ firmware updates by Oct 2025, now funded by sponsor tiers (Dell, Lenovo, NVIDIA, HP).Your hosting business has a real template. It also tells you the public registry should end up under a neutral foundation, as LVFS sits with the Linux Foundation.
Fuchsia DFv2A modern OS designed drivers as isolated components in driver hosts, aiming for "write once, run on many platform versions".Google still has not reached a stable driver ABI. Stability is hard even inside one company. Version the spec carefully from day one.
WASI hardware drivers (arXiv 2410.22919, NOMS 2025)USB and I²C drivers running inside WebAssembly, with at most ~8% overhead versus native USB APIs.Your Wasm logic sandbox is viable. Watch start-up cost for low-latency devices.
Rust for Linux (permanent since Dec 2025)Memory-safe drivers are now mainstream in Linux.Rust for the runtime is the right call and will be familiar to kernel people.
Kernel AI policy (Linux 7.0, 2026)Linux allows AI-assisted patches with human accountability. In Aug 2026 the staging tree began rejecting LLM-generated patches, and the wireless maintainer is filtering hard.Phase 3's "generate kernel drivers for upstream" must be human-owned, hardware-tested and disclosed. Otherwise it will damage your reputation with exactly the people you need.

Market scan: no company is shipping a cross-OS, AI-drafted driver platform today. The adjacent work is research (DevGen, ACL 2026, which turns Linux drivers into QEMU device models), datasheet-extraction tooling, and individual developers using LLMs to write one driver. The space is open, which also means you must create the demand.

04Architecture

The single most important design choice: split the problem into devices, classes and OSes, so the work adds instead of multiplies.

N devices × M OSes → N descriptions + C classes × M OS adaptersWith 10,000 devices, 20 classes and 5 OSes: 50,000 drivers become 10,000 descriptions plus 100 adapters, and the descriptions are mostly AI-drafted.

Your original plan has the runtime "expose the device to the OS through a standard interface" but does not say what that interface is. That is the gap. Without it, apps would have to talk to our API directly, and nothing existing (games, audio apps, terminal programs) would see the device. The fix is a class surface layer: each device class maps to the interface each OS already uses.

This table is your "blame model" from Part 5 made concrete. Every test report and every error message names one of these five layers.

Two open contracts that let any OS join

  • Host Interface (below the runtime): the complete list of what an OS must provide, with exact semantics, as a prose spec, a Rust trait (dd-host) and a C ABI (dd_host.h). Linux, macOS and Windows are the first three implementations; FreeBSD is the proof that a fourth OS can port from the docs alone.
  • Client protocol (between any OS and the storage): match-key lookup, OCI pulls, TUF freshness and revocation, Sigstore verification, private-content decryption, offline bundles, privacy rules. Our agent is one implementation; an independent Python client proves the spec is complete.

Linux already contains most of the pieces of a standard driver description, scattered across subsystems. Copy the shapes, so kernel people recognise them and so open descriptions can later be turned into kernel drivers.

For each one we can check an AI-drafted description against the register addresses, scale factors and IDs the kernel driver uses. That gives a measurable benchmark before a single vendor signs up (details in section 08).

06The description spec

Keep your section list (identity, interfaces, commands, state machine, timing, safety, tests, visibility, spec version). Changes:

  • Author in YAML, validate with JSON Schema 2020-12. Humans and LLMs both write YAML well, and comments survive. JSON Schema stays the canonical definition, exactly as dt-schema does.
  • Add a match: section in modalias style, and an expose: section mapping commands to a device class. Without these, the agent can't find drivers and the OS can't see devices.
  • Stack transports. A BME280 sensor behind a USB-to-I²C bridge is usb → i2c-bridge → i2c device. One bridge description serves every I²C chip, which multiplies coverage.
  • Use CEL (Common Expression Language) for conversions and guards. It is non-Turing-complete, sandboxed and already used by Kubernetes. Never invent an expression language.
  • Units as UCUM codes (Cel, Pa, mA), so conversions are checkable.
  • Importers instead of re-typing. Read CMSIS-SVD and SystemRDL register maps, USB descriptors, HID report descriptors, and SCPI command sets straight into the spec.
  • Profiles per class (sensor.temperature, input.keyboard, serial.uart) that say which fields are required, so the validator can say "a temperature sensor must expose a channel in Cel".
  • Safety fields need a human signature. The schema marks them, and the registry refuses to publish if the vendor did not sign them personally.

Example: POC 1 device description

# pico-thermo.yaml : Pico acting as a vendor-class USB device with an LED and its built-in temperature sensor
spec: driverdesk/0.1
device:
  id: example.pico-thermo
  name: Pico Thermo LED
  vendor: { name: Example Labs }
  version: 1.0.0
  classes: [sensor.temperature, light.indicator]

match:
  - bus: usb
    vid: 0x1209                    # pid.codes test IDs for our own fixtures
    pid: 0x0001
    interface_class: 0xFF          # vendor-specific, so no OS claims it first

transport:
  usb:
    interface: 0
    endpoints:
      out: { address: 0x01, type: bulk }
      in:  { address: 0x81, type: bulk }
  framing: { header: u8, length: u8, payload: bytes(length), check: crc8-smbus }

commands:
  hello:     { send: { header: 0x01 }, expect: { header: 0x81 }, timeout_ms: 50 }
  read_temp:
    send:    { header: 0x10 }
    expect:  { header: 0x90, payload: { raw: i16le } }
    output:  { celsius: { cel: "double(raw) / 100.0", unit: Cel } }
    timeout_ms: 50
    retries: 2
  set_led:
    send:    { header: 0x20, payload: { on: bool, level: u8 } }
    expect:  { header: 0xA0 }

safety:                            # vendor must sign this block
  limits:
    set_led.level: { max: 200, reason: "LED rated 20 mA at 3.3 V" }
  rate:
    set_led: 100/s

states:
  initial: off
  transitions:
    - { from: off,    to: idle,   do: [hello, { wait_ms: 10 }] }
    - { from: idle,   to: active, on: request }
    - { from: active, to: idle,   on: { idle_ms: 5000 } }

expose:
  - { class: sensor.temperature, channel: temp0, read: read_temp.celsius }
  - { class: light.indicator,    channel: led0,  write: set_led }

tests:
  - { name: room_temperature, call: read_temp, expect: { celsius: { between: [5, 45] } } }
  - { name: led_on,  call: set_led, args: { on: true,  level: 100 }, expect: ok }
  - { name: led_cap, call: set_led, args: { on: true,  level: 255 }, expect: rejected_by_safety }

visibility: { default: public }

Example: logic module interface (WIT, Wasm Component Model)

package driverdesk:logic@0.1.0;

interface device {
  variant value { int(s64), float(f64), boolean(bool), bytes(list<u8>) }
  record field { name: string, val: value }

  /// Calls a command declared in the description.
  /// The runtime checks the safety envelope and permissions before anything reaches the bus.
  call: func(command: string, args: list<field>) -> result<list<field>, string>;
}

world sensor-filter {
  import device;
  export process: func(channel: string, sample: f64) -> f64;
}

The logic module never sees raw USB or memory. It can only call commands that the description declares, and only within the declared safety limits. Vendors can write it in Rust, C, Zig, Go (TinyGo) or AssemblyScript.

Spec governance

  • Write it as an RFC-style document with MUST/SHOULD (RFC 2119), numbered sections and an example for every field, as you planned.
  • Semantic versioning with a written compatibility promise: a 1.x runtime runs every 1.y description.
  • Changes go through public proposals (like Rust RFCs or Python PEPs). This is what lets you hand it to a foundation later.
  • License the spec text CC-BY-4.0 with a royalty-free patent pledge, so hardware companies' lawyers can say yes.

08AI: the hardware developer owns the driver

The goal is that a hardware engineer who has never written a driver can go from datasheet to a signed, cross-OS driver in an afternoon, and stays the owner of it. The AI drafts, tests and explains. The vendor decides and signs.

The drafting pipeline

  1. Ingest. PDF to text and page images. Extract register tables with table tools first, and fall back to vision on the page image when tables are drawn as pictures.
  2. Extract per section with structured outputs. The JSON Schema of the spec is the output schema. Every field comes back as {value, confidence, evidence: {doc, page, quote}}.
  3. Cross-check. Deterministic checks the model can't skip: overlapping register addresses, unit mismatches, timing that contradicts the state machine, IDs that disagree with the USB descriptor.
  4. Validate loop. Run dd-spec; feed errors back; at most N rounds. Nothing reaches a person until it validates.
  5. Simulate. Generate a mock device from the description and run its own tests against it. This catches internal contradictions without hardware.
  6. Bench agent (hardware in the loop). The vendor runs our agent with the real device plugged in at their desk. The AI runs read-only probes and the declared tests, compares results with the draft, and proposes fixes, such as "register 0xD0 returned 0x60, the datasheet chip ID; field confirmed". It may never write outside the declared safety envelope, and the envelope itself must be human-signed first.
  7. Review. The portal sorts fields by risk × uncertainty and shows each one next to the datasheet passage it came from. Safety fields always need explicit human approval.
  8. Sign and publish. The vendor signs with their key. The AI is never a signer.

Beyond the first draft

  • Trace mode (POC 5): pcap plus a short note ("I pressed button A then B") produces a protocol hypothesis, which the bench agent then confirms by replaying safe commands.
  • Driver import: point it at an existing open driver (Linux, Zephyr, Arduino library) to produce a description. Check licences: facts like register addresses are generally not copyrightable, but get legal advice before importing from GPL code at scale.
  • Maintenance: when a vendor uploads a new datasheet revision, the AI diffs it against the description and opens a proposed change. When an OS update breaks a class surface, the harness pinpoints the layer and the AI drafts the fix for our adapter.
  • Support: the first-line support bot reads harness reports, which works because every failure names its layer.

Measure it: a Linux-grounded benchmark

Before POC 3, build an eval set of about 50 chips that have both a public datasheet and a mainline Linux driver (Bosch BME280/BMP280, TI TMP117, ST LIS3DH, Sensirion SHT3x, InvenSense MPU-6050 and so on). Ground truth is the register addresses, chip IDs, scale factors and init sequences in the kernel driver. Score every AI draft per field. Report:

  • Field accuracy on first try, and after the validate loop.
  • Fields the AI marked high confidence that were wrong. This number must trend to zero, because it decides whether humans can trust the confidence scores.
  • Minutes of human editing to reach passing tests.

Publish the benchmark openly. It becomes a credibility asset, and model providers may even compete on it.

Guardrail

Generated Linux kernel drivers (Phase 3) go upstream only with a named human author who tested on real hardware, using the kernel's Assisted-by disclosure. Staging maintainers already reject LLM-generated patches. One sloppy submission could close the door for years.

09Proof-of-concept stages, revised

Your six stages are in the right order. Changes: a bootstrap stage so an AI can build and test unattended, a zero stage for the spec and benchmark, a real chip behind the Pico so the AI stage uses a real datasheet, a stage proving the device appears as a native OS device, and a final stage for OS writers. Each stage has a detailed plan in the repo (plans/) with pass criteria, tasks, open questions with default answers, and known traps.

POC 2 · One description, every OS 3–4 weeks

First-try and post-loop accuracy, confident-and-wrong rate, calibration, cost. If first-try accuracy stays under 60%, the plan pivots toward trace and import tools.

12How it scales

Engineering: build less than you think

  • Storage and delivery: descriptions and logic modules are OCI artifacts, content-addressed and cached by any CDN. A self-hosted node is an OCI registry plus our small index. No custom package infrastructure.
  • Trust: Sigstore for signatures and the transparency log, TUF for freshness and revocation. Both are what PyPI, npm and Kubernetes use.
  • Coverage: grows by descriptions, not code. Our code grows only by classes × OSes, about 100 adapters total for the beachhead.
  • Runtime footprint: one process per device keeps failures isolated. Idle devices cost almost nothing.

Device lab: three tiers

  1. Simulated devices generated from descriptions and from recorded traces. They run in CI on every change, for free, on every OS. This should catch about 80% of breakage.
  2. Distributed labs. Vendors and contributors run our lab runner on their own hardware, the way GitHub Actions supports self-hosted runners. Results are signed in-toto attestations, so they can be trusted and shown on a device's page.
  3. Our own racks for certification only: per-port power switching (uhubctl-compatible hubs or Acroname), USB switches, and Linux, macOS and Windows machines plus OS beta builds. Start with one desk; grow to racks when certification revenue pays for them.

13Security changes

Your threat list and defences are good. Five corrections:

  1. "Private" means access-controlled, not secret. A description or Wasm module that runs on a customer's machine must be decrypted there and can be read or decompiled. Vendor-held keys protect it at rest and in transit and limit who can download it. Say this plainly to vendors. Truly secret logic belongs in device firmware.
  2. Matching by USB IDs can be spoofed. A malicious device can claim to be anything. The rule that makes this safe: a driver may only touch the device it matched, through its own bus handle, and never host resources. A spoofed device then only gets a driver for something it isn't, which is harmless.
  3. Two sandboxes, not one. Wasm for logic, and an OS process sandbox (landlock + seccomp, macOS sandbox, AppContainer) around the whole runtime. Run each device in its own process.
  4. Revocation through TUF metadata expiry. Agents refuse to start drivers whose metadata is older than a set window when online, and offline bundles have explicit expiry dates. Test revocation monthly, as you planned.
  5. Safety envelope signed by a person. No AI process, ours or the vendor's, can approve or loosen safety limits.

Keep the rest: reproducible builds, signed releases, audits before Phase 2, bug bounty, SOC 2 when enterprise customers arrive, no user tracking on lookups.
