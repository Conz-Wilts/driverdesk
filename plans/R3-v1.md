# R3 — Version 1.0 and growth

- Status: not started · Depends on: R2 gate · Branch: `stage/r3` · Horizon: months 20–36
- **R3.T0 is mandatory: expand this plan to P1-level detail before building.**

Claim: the standard outlives the startup — open descriptions can become upstream kernel drivers, a second OS adopts the runtime, and the spec belongs to a neutral foundation.

## Exit criteria (draft)

1. **Kernel driver generation**: open descriptions for I²C sensors generate Linux IIO/hwmon drivers that pass `checkpatch.pl`, build clean, and pass HIL tests. Upstream submissions are made **only by a named human author** with `Signed-off-by`, hardware-tested, with the kernel's AI-assistance disclosure. ≥ 3 drivers merged upstream.
2. Device classes added: audio (via PipeWire / AudioServerPlugIn / Windows shim), network (TUN/utun/Wintun), basic storage (ublk), basic cameras (PipeWire/CoreMediaIO/MF virtual camera).
3. Per-OS class shims (macOS DriverKit, Windows UMDF/KMDF) for classes without userspace surfaces, signed and maintained.
4. RFC for a small, open "driver host" kernel module on Linux posted to the relevant mailing list with a working prototype — human author, as above.
5. A second OS (a hobby OS such as Redox/Haiku/SerenityOS, or a BSD) runs the runtime with ≥ 10 devices.
6. Spec + public registry governance handed to a neutral foundation (Linux Foundation or similar).
7. Device lab v2: multiple racks, OS beta tracks, partner pre-release testing channel.
8. Hundreds of verified devices.

## Notes

The kernel community's reaction is the biggest risk here. Read `Documentation/process/` (including the coding-assistants policy) at R3.T0, follow subsystem etiquette exactly, start with one small, obviously useful driver, and let human authors lead every conversation.
